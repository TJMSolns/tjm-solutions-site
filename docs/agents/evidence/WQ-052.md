(3) Parallel baseline: same 6 pages at `xargs -P 6` in **6.159s**. Small samples are dominated by

(4) Full sweep, the decisive measurement: all **74 pages** at `xargs -P 6`, **dark theme** (see the
correction note below), in
**60.303s** (60.3 / 74 = 0.815s/page, `user 2m13s` confirming real parallelism). Both themes is 148
runs, extrapolating to ~2 minutes — linear in run count, since each pa11y invocation is an
independent process.

Invariance-recheck: The decision does not rest on the extrapolation alone. The load-bearing claim is
that the full sweep is affordable, and that was measured directly at 74 pages rather than inferred
from the 6-page sample — which matters, because the 6-page sample would have implied ~2.15s/page
serial and overstated the cost by roughly 2x. The dual-theme figure is the one extrapolated value,
and it is a doubling of run count against a per-run cost measured across 74 real invocations, not a
projection from a micro-benchmark.

The decision was also stress-tested against the alternative it displaces. Option (a)'s unsoundness
was not taken on faith from the WQ-052 row: the mechanism is that page accessibility depends on
shared CSS, components, tokens and Docusaurus version, and this session produced a concrete instance
— the WQ-056 contrast failure is a single shared syntax-highlighting token (`rgb(98, 114, 164)` at
3.03:1) manifesting on 3 unrelated pages, none of which would be re-checked by a source-change-keyed
cache. That is the same failure class as WQ-042's gray-scale token bug, now observed twice.

Strongest evidence that full coverage is the right call, and independent of any timing argument: the
measuring run was itself the first full sweep ever performed on this site, and it immediately found a
live WCAG2AA violation on production (WQ-056) that the incumbent 4-URL gate structurally could not
find, since none of those four pages contains a code comment. A 10% random sample would have found it
only on a lucky draw, and non-reproducibly.

Residual risk, stated plainly: the policy is measurement-dependent and the site will grow. That is why
POL-003 carries an explicit revisit trigger at 5 minutes wall-clock (~145 pages at the measured rate)
and names option (c) as the successor design, rather than leaving a future session to quietly narrow
the gate.

## Correction 2026-08-18 — theme attribution was inverted (verifier VETO)

The sweep described above ran in **dark** theme, not light. `docusaurus.config.ts` sets
`colorMode.defaultMode: 'dark'` with `respectPrefersColorScheme: true`, and headless Chrome reports
`prefers-color-scheme: dark`. Confirmed directly against the served build:
`prefersDark=true, data-theme=dark, localStorage.theme=null, body background=rgb(19, 19, 21)`.
The doer's own evidence corroborated it unnoticed: `rgb(98, 114, 164)` is Dracula's comment colour,
i.e. `prism.darkTheme` (config line 203), and pa11y's remedy "change text colour to `#fefeff`" only
makes sense against a dark background.

This inverted the claim in three records (all now corrected): this artifact, POL-003's Context and
Consequences, and the WQ-056 row. **The untested half was the worse half.** Re-running the full
74-page sweep with the theme forced to light (`emulateMediaFeatures` + `localStorage.theme='light'`,
`data-theme=light` asserted on every page):

| Theme | Failing pages | Total errors | Distinct failing tokens |
|-------|---------------|--------------|-------------------------|
| dark  | 3             | 5            | 1 (`rgb(98, 114, 164)`) |
| light | **7**         | **233**      | **4** |

Light-theme failures by page: `/articles/2026/04/21/protocol-stack-agent-native-commerce` (95),
`/mdslides/docs/themes` (75), `/articles/2026/04/21/capability-surfaces` (32),
`/mdslides/docs/writing-slides` (20), `/mdslides/docs/configuration` (6),
`/mdslides/docs/speaker-view` (3), `/mdslides/docs/navigation` (2). By token colour:
`rgb(54, 172, 170)` ×135, `rgb(227, 17, 108)` ×83, `rgb(0, 164, 219)` ×10, `rgb(153, 153, 136)` ×5.
Light mode is user-reachable (`disableSwitch: false`, `respectPrefersColorScheme: true`), so these are
live production failures, not a test artefact.

**The decision in POL-003 is unaffected, and strengthened.** Full coverage was chosen because sampling
cannot be trusted to find systemic defects; the inversion is a direct demonstration — a whole theme,
carrying 233 of the 238 total errors, was invisible because nobody checked which theme was actually
rendering. Timing also improved on re-measurement: driving the theme programmatically with a shared
Puppeteer browser did 74 pages in **15.6s**, against 60.3s for the pa11y CLI spawning a browser per
page, so both themes is roughly **31s** — well inside POL-003's 5-minute trigger.

**Implementation note for WQ-051 — corrected after a second VETO.** An earlier version of this
artifact claimed the config-file `actions` route was broken and that theme driving therefore *required*
the programmatic pa11y API. That was a misdiagnosed experiment on my part, and it would have imposed a
false constraint on WQ-051. pa11y 9.0.1's CLI genuinely has no `--actions` flag and no `beforeScript`,
but `node_modules/pa11y/lib/pa11y.js` implements `options.actions`, reachable via `pa11y -c <config>`.
The ~32s timeout came from my own wait predicate: I clicked the colour-mode toggle then waited for
`html[data-theme='dark']` — on a site that *starts* dark and becomes *light* on click, so the predicate
could never be satisfied. Re-tested both ways on `/mdslides/docs/navigation`:
`wait for element html[data-theme='light'] to be added` → **3.016s**, returns light-theme results;
`...data-theme='dark'...` → **32.940s**, `TimeoutError`. Both routes are available to WQ-051; the
programmatic API is simply faster at scale (0.211s/page vs ~3s/page).
